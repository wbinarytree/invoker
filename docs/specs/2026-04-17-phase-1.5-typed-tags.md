# Phase 1.5 — Typed Tag Families, Ability-Level Extraction, and Role Context

> Superseded on 2026-04-18 as an active roadmap document. It contains useful representation ideas, but the project has shifted to a benchmark-first KG validation path before broad schema rollout. See [docs/CURRENT_DIRECTION.md](/Users/yaoda/Projects/invoker/docs/CURRENT_DIRECTION.md:1).

**Date:** 2026-04-17
**Status:** superseded draft — preserved for local trace
**Scope:** medium; new prompts, new schema, new vocabulary file, validator changes, `schema_version` bump.
**Depends on:** Phase 1.1 closure (other agent).

---

## Motivation

Phase 1 shipped a hero knowledge base with one tag family (`functional_tags`) and prose-only synergy/counter reasons. That shape answers "what does this hero do?" but not "what does this hero *need*?" or "what does it *cost* us?" — the questions a drafting agent actually asks.

An expert review recommended seven upgrades. We accept three (typed reason factors, requirement/liability tag families, per-hero role distribution), defer the rest (per-pair role-conditional scoring, lane templates, team/player scope, graph split, draft-state query API), and add one of our own (ability-level tagging).

This is not a full redesign. It is a targeted schema expansion that changes *what we extract* without reshaping the pipeline or the storage model.

---

## Goals

1. Hero tags split into three families with a shared closed vocabulary: `capabilities`, `requirements`, `liabilities`.
2. `capabilities` split into **observed** (per-ability, quoted evidence) and **emergent** (hero-level kit synthesis, multi-ability evidence).
3. Tags primarily live at the **ability level**; hero-level observed tags are a derived aggregation. Emergent tags are hero-level only.
4. Edge records carry typed `reason_factors` alongside prose `llm_reason`.
5. Each hero carries a pro-cohort `position_distribution` derived from OpenDota pro matches.
6. Schema reserves empty slots for future modifier families (`facets`, `shard`, `scepter`, `talents`); Phase 1.5 extracts none of these. See §Modifier-ready schema.
7. Validator enforces vocabulary membership and evidence-grounding per tag family.

## Non-goals (explicitly deferred)

- `draft_traits` family (reveal cost, flex value, first-phase safety).
- Per-pair role-conditional synergy scoring (our data sources don't provide it).
- Lane templates as first-class nodes.
- Team-slug / player identity with roster_hash and backoff.
- Splitting hero JSON into separate facts/relations/views files.
- Draft-state query API surfaces (`candidate_bundle`, `requirements_filled`, etc.).
- **Modifier extraction** (talents, shard, scepter, facets, innate). Schema slots are reserved per §Modifier-ready schema so Phase 2 is additive, but no modifier content is extracted in Phase 1.5. Facets are moot in 7.41 (removed from the patch) but the slot remains.

These may return in Phase 2 once the drafting agent consumes Phase 1.5 artifacts and shows us what's missing.

## Workstream A — Typed tag families and reason factors

### Vocabulary file

New file: `src/invoker/taxonomy/vocabulary.py` (or `.json`).

A single closed vocabulary, partitioned by family. Seed list (indicative, expect to grow under review):

**capabilities_observed** — things a single ability exhibits directly:
```
initiation, hard_disable, soft_disable, silence, mute, break,
save, dispel_basic, dispel_strong, heal,
armor_reduction, magic_amplification,
magic_burst, physical_burst, sustained_damage,
aoe_damage, single_target_damage,
waveclear, push, tower_damage, roshan_damage,
frontline, mobility, catch, escape,
vision, invisibility_detection,
illusion_creation, summon
```

**capabilities_emergent** — patterns that only exist when abilities combine. Seed list is small and grows cautiously (see Risk register):
```
self_sufficient_pickoff, armor_amplified_burst,
mobile_initiator, teamfight_anchor, pickoff_specialist,
zone_control, setup_and_reposition, lockdown_chain
```

**requirements** — things a hero needs from the rest of the team:
```
needs_setup, needs_followup_damage, needs_frontline,
needs_save, needs_vision, needs_dispel,
needs_waveclear, needs_farm_priority
```

**liabilities** — costs a hero imposes on the team:
```
low_waveclear, low_tower_damage,
mana_dependent, farm_dependent, level_dependent,
kiteable, illusions_vulnerable, no_disjoint,
weak_lane, short_range_required
```

Vocabulary grows organically. Extractor may propose new terms; additions land in the vocabulary file under review. Unknown terms in extraction output are rejected by the validator.

### Ability-level schema

Per-hero JSON gains an `abilities` block:

```json
{
  "abilities": [
    {
      "ability_id": "slardar_corrosive_haze",
      "name": "Corrosive Haze",
      "description": "...",
      "capabilities": ["armor_reduction", "vision"],
      "tag_sources": [
        {"tag": "armor_reduction",
         "quote": "reduces the target's armor by 20/25/30"},
        {"tag": "vision",
         "quote": "reveals the target"}
      ]
    },
    ...
  ]
}
```

`tag_sources` quotes are mandatory for capability tags — they are observable from text.

### Hero-level schema

```json
{
  "capabilities_observed": ["armor_reduction", "initiation", "mobility", ...],
  "capabilities_emergent": ["self_sufficient_pickoff", "armor_amplified_burst"],
  "requirements": ["needs_followup_damage"],
  "liabilities": ["short_range_required"],

  "capability_observed_sources": {
    "armor_reduction": ["slardar_corrosive_haze"],
    "initiation": ["slardar_slithereen_crush", "slardar_sprint"]
  },
  "capability_emergent_evidence": {
    "self_sufficient_pickoff": {
      "derived_from": ["slardar_sprint", "slardar_slithereen_crush",
                       "slardar_bash", "slardar_corrosive_haze"],
      "rationale": "Gap close + stun + armor amp + bash lets him solo-kill supports without team setup."
    }
  },
  "requirement_evidence": {
    "needs_followup_damage": {
      "derived_from": ["slardar_slithereen_crush", "slardar_corrosive_haze"],
      "rationale": "Provides armor reduction and AoE stun but no burst damage of his own."
    }
  },
  "liability_evidence": {
    "short_range_required": {
      "derived_from": ["slardar_slithereen_crush", "slardar_corrosive_haze"],
      "rationale": "All damage and disables require melee range."
    }
  }
}
```

Three evidence models, one per family:

- **Observed capabilities** are read directly from a single ability. Each carries a quoted `tag_source` at the ability that exhibits it. Hero-level `capabilities_observed` is the union of ability-level capabilities. `capability_observed_sources` records which ability exhibits each.
- **Emergent capabilities** are synthesized from how the kit combines. No single ability deserves the tag; the combo does. Each carries `derived_from: list[ability_id]` with ≥2 entries from the hero's own abilities, plus a short `rationale`. Slardar's "self_sufficient_pickoff" and "armor_amplified_burst" are canonical examples — no single ability produces them.
- **Requirements and liabilities** are hero-level inferences about what the kit *needs* or *costs*. Same `derived_from` + `rationale` model as emergent capabilities. No quoted evidence — the ability text does not state a requirement; it's read between the lines.

Query-time: consumers treat `capabilities = capabilities_observed ∪ capabilities_emergent`. The split is for provenance, not for querying.

This is the (iii) option from the discussion, extended to handle the emergent-combo case (Slardar's kit-level pickoff pattern, Pangolier's base mobile-initiator pattern): honest about observed-vs-synthesized, keeps quoted grounding where it's possible, avoids faking evidence where it isn't.

### Reason factors on edges

Edge records gain `reason_factors`:

```json
{
  "hero_id": 120,
  "score": 0.08,
  "games": 50,
  "confidence": "high",
  "reason_factors": ["armor_reduction", "physical_burst_followup"],
  "llm_reason": "Slardar's armor reduction amplifies Pangolier's physical burst."
}
```

Reason factors draw from an **extended** vocabulary — the capability/requirement/liability terms plus a small set of relational operators:
```
fills_requirement_for_<req>, breaks_<capability>,
dispels_key_debuff, outranges, counters_illusion_play, counters_summon_play
```
(Full list lives in the same vocabulary file, under a `reason_factors` section.)

Prose `llm_reason` stays as a convenience field. `reason_factors` is the durable, queryable artifact.

### Prompt structure

Adopting option (ii) from the discussion:

**Prompt 1 — `extract_ability_capabilities` (per ability, new).**
Input: ability name + description + hero name + hero roles. Output: `{capabilities: list[str], tag_sources: list[{tag, quote}]}`. One call per ability, typically 3-5 per hero.

**Prompt 2 — `extract_hero_synthesis` (per hero, new).**
Input: hero name, roles, and the *already-extracted* per-ability capability tags (not raw ability text). Output: `{capabilities_emergent, capability_emergent_evidence, requirements, requirement_evidence, liabilities, liability_evidence}`. One call per hero. Covers all three hero-level synthesis families in one pass so the model can reason about tradeoffs (a hero whose kit is "self_sufficient_pickoff" usually isn't "farm_dependent", etc.).

**Prompt 3 — `edge_reasons_batch` (existing, modified).**
Output JSON items now include `reason_factors` alongside `reason`. Input header carries hero A's capability/requirement/liability lists. Each edge item carries hero B's capability/requirement/liability lists.

### Call budget

Per hero:
- N ability capability extractions (typical N = 3-5)
- 1 hero-level requirement/liability synthesis
- 1 batch reason call

For Slardar + Pangolier: roughly 8-12 ability calls + 2 synthesis + 2 batches = **12-16 calls** vs. the current **4**. Meaningful jump. Cache makes reruns free. For full-roster bootstrap (123 heroes × ~4 abilities ≈ 500+ calls) this is only tractable on a paid plan or with Gemma's 100 RPD tier.

### Validator changes

1. All tags in all families (`capabilities_observed`, `capabilities_emergent`, `requirements`, `liabilities`, `reason_factors`) must belong to the closed vocabulary. Unknown tag → reject.
2. Each observed capability tag must have a `tag_source` whose quote substring appears in the referenced ability's description.
3. Each emergent capability tag must have `derived_from` with **≥2 distinct ability_ids belonging to the hero**. A single-ability emergent tag is almost certainly a mislabeled observed tag; reject and surface a warning.
4. Each requirement/liability tag must have `derived_from` with ≥1 ability_id belonging to the hero.
5. All `derived_from` and `tag_sources` references must resolve to abilities the hero actually owns.
6. `reason_factors` must be vocabulary-valid and the list must be non-empty.
7. Grounding (tightened from Phase 1): a synergy/counter `reason_factors` list is valid iff every factor either (a) matches a capability (observed or emergent) of hero A, (b) matches a capability of hero B, or (c) is a relational operator (`fills_requirement_for_*`, `breaks_*`, etc.) whose subject is satisfied by the other side's capability/requirement list.

## Workstream B — Per-hero role distribution

### Source

OpenDota `/api/proMatches` gives player_slot per pick. Slot → position mapping is approximate but adequate for pro: slot 0-4 are Radiant 1-5, 128-132 are Dire 1-5. Slot does not cleanly map to role (1/2/3/4/5) — role inference needs lane and net-worth data, which comes from parsed matches (`/api/matches/{id}`).

Two options:

- **(B1) slot-only distribution**, cheaper: `slot_distribution: {"radiant_slot_0": 0.12, ...}`. Honest about what the data says. Low signal for drafters.
- **(B2) role-inferred distribution**, fuller: fetch parsed match detail for a sample, bucket by role from lane + net_worth rank. Real drafting signal but needs many more API calls.

Recommendation: **B2 against a sample of ~500 recent pro matches per patch**, stored as:

```json
{
  "position_distribution": {
    "pro": {"1": 0.02, "2": 0.05, "3": 0.73, "4": 0.18, "5": 0.02,
            "games": 412, "sampled_matches": 500}
  }
}
```

Sample size cap makes this bounded; manifest records the sample. Alternative sources (STRATZ `heroStats.playerPosition` if exposed) are worth a probe before committing to parsed-match fetching.

### Out of scope for B

- Per-pair role-conditional synergy.
- Non-pro cohorts (immortal_pub, pub_all). Future.
- Role timeline (role shifts over a patch). Future.

## Modifier-ready schema

The drafting agent eventually needs to reason about configuration-sensitive heroes — heroes whose effective capabilities, requirements, and liabilities change based on which shard/scepter they buy, or which talents they pick. The canonical case: Pangolier's shard is weak in isolation but unlocks a strong kit-level combo. Tagging only base abilities misses this class of signal.

Phase 1.5 does **not** extract modifiers. But Phase 1.5 *does* reserve the schema slots for them, so Phase 2 is a purely additive extension rather than a breaking change.

### Reserved slots (empty in Phase 1.5)

```json
{
  "abilities": [...],
  "innate": null,
  "facets": [],
  "shard": null,
  "scepter": null,
  "talents": [],
  "capabilities_emergent_by_config": {}
}
```

- `facets` — list. Empty in 7.41 because the patch removed facets entirely (noted per user; verify against OpenDota constants before coding). Slot remains for historical-patch compatibility and possible future reintroduction.
- `shard`, `scepter` — a modifier object when Phase 2 extracts them, `null` otherwise.
- `talents` — list of talent objects by tier/branch.
- `innate` — per-hero innate ability object; extraction deferred to Phase 2.
- `capabilities_emergent_by_config` — Phase 2 landing site for configuration-sensitive emergent tags. Maps a config key (e.g., `"shard"`, `"facet:foo"`, `"talent_20:left"`) to a list of additional emergent-capability entries. A query-time composer resolves `capabilities(hero, shard=True, ...)` by merging `capabilities_emergent` with applicable entries from this map.

### Tag delta model (Phase 2 design sketch)

When modifier extraction lands, each modifier carries its own tag deltas:

```json
{
  "shard": {
    "description": "...",
    "modifies_ability": "pangolier_shield_crash",
    "adds_capabilities_observed": ["..."],
    "removes_capabilities_observed": [],
    "adds_capabilities_emergent": [
      {
        "tag": "rolling_thunder_chain_cast",
        "derived_from": ["pangolier_rolling_thunder", "pangolier_shield_crash"],
        "rationale": "Shard lets Shield Crash be cast during Rolling Thunder, enabling a combo no base ability produces alone.",
        "requires_config": ["shard"]
      }
    ]
  }
}
```

Emergent tags carry `requires_config` so the composer knows which settings activate them.

### Why this isn't wasted work

Three reasons Phase 1.5 extraction is reused verbatim when modifiers land:

1. **Base ability tags don't change.** Numbers-only talents ("+40 damage") don't alter capability tags. Only behavior-changing modifiers do, and those land as deltas, not rewrites.
2. **Base emergent tags are stable.** Slardar's `self_sufficient_pickoff` holds regardless of shard/talents. Pangolier's base `mobile_initiator` holds; shard adds a new emergent tag, doesn't invalidate the base one.
3. **The drafting agent's current state is pre-facet/pre-modifier.** Pool-based inference pre-draft doesn't know modifier choices yet. Phase 1.5 delivers what the agent can consume today.

### Out-of-scope edge cases

- **Innate abilities.** Deferred to Phase 2 despite being base-kit. Many innates are passive and low-signal; extraction quality needs separate prompt engineering.
- **Identity-flipping facets** (Dawnbreaker-style). Not applicable in 7.41. If facets return in a later patch, Phase 2 will need a `config_aware: bool` flag on affected heroes with emergent tags skipped or caveated.

## Pipeline impact

Stages changed:
- `extract` — was one LLM call per hero; becomes ability-fanout + hero synthesis. Provenance records both prompt versions and both input hashes.
- `reason` — prompt gains `reason_factors` output field; validator extended.
- `assemble` — merges per-ability tags into hero-level aggregates; records `capability_sources`.
- `write` — new JSON shape.

Stages unchanged: `fetch`, `bundle`, `derive`, `summarize`, `finalize`.

Orchestrator call budget per hero goes from 2 to ~N+2. `--max-reason-edges` (from Phase 1.1) still bounds the batch call.

## Risk register

1. **Vocabulary drift.** Extractor proposes synonyms of existing terms under slightly different spellings. Mitigation: validator rejects unknown terms; the human curator (us) folds variants into the canonical form when extending the vocab.
2. **Emergent capability hallucination.** Highest risk of the three families. LLM is likely to claim plausible-sounding emergent tags ("teamfight_anchor" because it sounds right). Mitigation: seed vocab starts very small (8 terms); add a new emergent term only after seeing it justified on ≥2 heroes; validator requires `derived_from` ≥2 abilities; spot-check every emergent tag on Slardar / Pangolier runs before accepting the vocab expansion.
3. **Requirement/liability hallucination.** These tags are inferred, harder to validate than observed. Mitigation: `derived_from` must reference real abilities; `rationale` must be one sentence; spot-check during Slardar / Pangolier runs before going broader.
4. **Call budget explosion.** Ability-level extraction is 3-5× the call count per hero. Mitigation: cache; bounded roster via `--heroes`; move to paid tier before full bootstrap.
5. **B2 data cost.** Fetching parsed matches is heavy. Mitigation: probe STRATZ first; cap sample size; fetch once per patch.
