# Phase 1.2 — Pipeline Correctness and Tag-Grounded Candidates

**Date:** 2026-04-17
**Status:** superseded draft — preserved for local trace
**Scope:** small-medium; orchestrator split, guard, new candidate source, no schema change.
**Depends on:** Phase 1.1 closure.

---

## Motivation

Four correctness gaps surfaced during Phase 1.1 testing:

1. **Two-pass gap.** The orchestrator runs extract → reason per hero sequentially. When Slardar's reason batch runs, Dragon Knight and Dark Seer have not been extracted yet — their `hero_b_tags` are empty. The LLM is asked to write tag-grounded reasons for heroes it has no tag data for, triggering thinking loops and empty responses.

2. **Wasted LLM call guard.** Even with a correct two-pass pipeline there will be edge cases where hero_b tags are unavailable (extraction failed, new hero). Calling the reason batch when no hero_b has tags produces unreliable output and burns quota.

3. **Candidates come only from Stratz.** Stratz win-rate correlation is the sole source of synergy/counter candidates. The extracted functional tags are only used to explain statistically-derived relationships — they are never used to *discover* them. This means tag-obvious relationships (e.g. `physical_damage_amplifier` + `physical_carry`) can be missed or buried if Stratz sample size is thin.

4. **No-data contract.** `derive.merge_matchups` silently drops OpenDota rows with `games_played == 0`. The repo rule is that absence must be explicit — a zero-games matchup is not "no relationship," it is "no data yet." Dropping it is indistinguishable from "never observed" when downstream consumers read the hero file. This was deferred from Phase 1.1 §9.

---

## Goals

1. Split the orchestrator into two explicit passes so all hero tags are present before any reason batch runs.
2. Add a guard that skips the reason batch (and logs why) when tag coverage is below a threshold.
3. Introduce a tag-inference candidate source that uses extracted functional tags to generate synergy/counter pairs independently of Stratz, then merge the two sources.
4. Stop dropping zero-game matchup rows. Emit them as explicit no-data edges (`score=None`, `games=0`, `confidence="none"`) and protect the behavior with a validator.

---

## Non-goals

- Schema changes. `functional_tags` shape is unchanged; Phase 1.5 adds typed families.
- Full typed-tag compatibility matrices. With Phase 1.1's flat tags, inference is limited to simple overlap rules. Phase 1.5 (requirements/liabilities) makes this richer.
- Replacing Stratz. Statistical evidence stays; this adds a second source and merges them.
- Inferring all O(n²) pairs. Only hero A's existing Stratz candidates are rescored/augmented, not the full hero roster.

---

## Change 1 — Two-pass orchestrator

Split `run_for_hero` into two functions:

```
extract_hero(bundle, client) → writes hero file with tags, no reasons
reason_hero(hero_id, patch, client) → reads written hero, adds reasons, rewrites
```

`bootstrap` in `cli.py` becomes:

```python
# Pass 1: extract all
for bundle in bundles:
    extract_hero(...)

# Pass 2: reason all
for bundle in bundles:
    reason_hero(...)
```

Each pass writes/updates the hero file independently so partial runs are resumable. If a hero's extraction file already exists and is cache-fresh, Pass 1 skips it (same caching logic as today).

`finalize_patch` runs after Pass 2, unchanged.

---

## Change 2 — Reason batch guard

Before building the `BatchReasonInput`, count how many candidate edges have `hero_b_tags`:

```python
tagged = sum(1 for e in candidates if e.hero_b_tags)
if tagged == 0:
    _trace(f"reason   skip    hero={hero_id}  (0/{len(candidates)} hero_b have tags)")
    # reasons stay empty; hero written without reasons
    # will be resolved when the relevant heroes are extracted (next run)
```

Threshold is `tagged == 0` for now. After Phase 1.5 ships typed families, this can become a richer coverage check.

## Change 3 — Tag-inferred candidates

### What it produces

A new function `infer_candidates(hero_a_tags, all_hero_tags) -> list[InferredEdge]` that scans the already-extracted heroes and returns (hero_b_id, relation, affinity_score) triples based on tag compatibility rules.

### Compatibility rules (Phase 1.2 seed, grows with Phase 1.5)

Synergy signals (A tags → B tags that complement):
```
physical_damage_amplifier  → any hero with single_target_damage or aoe_damage
aoe_disable / initiation   → any hero with high-damage burst (magic_burst, physical_burst)
vision_control             → any hero that requires vision gaps to engage
single_target_disable      → pairs with aoe_disable for lockdown chains
```

Counter signals (A tags → B tags that are vulnerable):
```
physical_damage_amplifier  → counters heroes with low physical resistance or healing-reliant heroes
single_target_disable      → counters mobile heroes (blink tag)
vision_control             → counters heroes with invisibility or fog-dependent abilities
```

Rules are stored in a small table in `src/invoker/pipeline/tag_affinity.py`, not hardcoded in the function. Phase 1.5 replaces this table with the typed vocabulary.

### Merge strategy

Stratz candidates are the primary source. Tag-inferred candidates:
- If a Stratz candidate also matches a tag rule → boost its confidence one level (low→med, med→high).
- If a tag-inferred hero is *not* in the Stratz top-20 → add as a candidate with confidence `low` and `games=None`.

The reason batch receives the merged set (capped at `max_edges` per relation, sorted by confidence then score). This means the LLM explains both statistically-validated and tag-inferred relationships.

`reason_factors` (Phase 1.5 field) will make the source of each edge queryable; for now the distinction is in the edge's `confidence` and `games` fields.

## Change 4 — No-data contract

### Behavior change

`derive.merge_matchups` currently does:

```python
if games == 0:
    continue  # src/invoker/pipeline/derive.py:108
```

Replace with:

```python
if games == 0:
    target = synergies  # or a dedicated no_data bucket; see below
    target[other] = StatisticalEdge(
        hero_id=other,
        score=None,
        games=0,
        confidence="none",
        source="opendota",
    )
    continue
```

Bucket routing: since we cannot tell synergy from counter without a score, zero-games edges are emitted into a **single no-data list** on the hero artifact, not split across `synergies` / `counters`. The writer already tolerates `score=None` per the dataclass type, but splitting by sign when sign is unknown would be dishonest. A new field `no_data_matchups: list[StatisticalEdge]` is added alongside `synergies` / `counters`.

Stratz edges with `matchCount == 0` (rare but possible) go to the same list.

Tag-inferred candidates from Change 3 are a separate concern — they have `games=None` (not observed) rather than `games=0` (observed, no sample). These keep flowing through `synergies` / `counters` with `confidence="low"` as drafted.

### Validator

Add `validate_hero_no_silent_drops(hero_raw, hero_written)` run during finalize:

- For each hero_id appearing in `hero_raw.opendota_matchups` or `hero_raw.stratz_edges`, assert it appears in exactly one of `synergies`, `counters`, or `no_data_matchups` on the written artifact.
- Fail finalize (not just warn) if a hero_id present in raw input is absent from all three lists.

Keeps the contract honest: the derive layer cannot silently drop data without the validator catching it.

## Pipeline impact

|---|---|

Call budget per hero: unchanged (still 1 extract + 1 reason batch). Tag inference is pure Python — no LLM calls. No-data change is pure Python.
